## Review Summary

The cleanup SQL is designed to clear operational workflow rows so Scenario A can determine whether Sprint 8 audit findings come from legacy/test data or active workflow defects.

The script intentionally preserves master/reference/context data:

- users
- roles
- permissions
- warehouses
- warehouse zones
- suppliers
- projects
- categories
- units
- settings/reference data

## Tables Cleared

### QC Operational Data

Statement:

```sql
TRUNCATE TABLE
  "qc_attachments",
  "non_conformance_reports",
  "qc_issues",
  "qc_results",
  "qc_inspections"
RESTART IDENTITY CASCADE;
```

Reason:

- Clears inspection execution, results, issues, NCRs, and QC evidence links.
- Keeps QC checklist master definitions.

Preserved:

- `qc_checklists`
- `qc_checklist_items`

Risk:

- Historical QC evidence and NCR audit trail will be removed from the validation database.

### Yard Operational Data

Statement:

```sql
TRUNCATE TABLE
  "yard_movements",
  "yard_item_placements",
  "yard_snapshots"
RESTART IDENTITY CASCADE;
```

Reason:

- Clears staged/removed items, Yard move history, and runtime snapshots.
- Leaves Yard physical layout intact.

Preserved:

- `yard_zones`
- `yard_rows`
- `yard_slots`
- `cranes`

Risk:

- Historical Yard movement trace is removed.
- Slot state must be reset after clearing placements; the script includes this reset.

### Components

Statement:

```sql
TRUNCATE TABLE
  "tasks",
  "component_timelines",
  "ComponentCosting",
  "components"
RESTART IDENTITY CASCADE;
```

Reason:

- Clears produced components, lifecycle timeline, and costing rows.
- Clears generic component-linked task rows so truncating `components` does not rely on hidden cascade behavior.
- Required so Scenario A can create exactly one controlled component.

Preserved:

- `projects`
- production master/reference tables

Risk:

- Existing project-linked component visibility is removed in the validation database.

### Yard Slot Reset

Statement:

```sql
UPDATE "yard_slots"
SET
  "status" = 'AVAILABLE',
  "currentStackLevel" = 0,
  "updatedAt" = NOW();
```

Reason:

- After clearing placements, Yard slots must not remain marked occupied.

Preserved:

- Slot layout, coordinates, zone/row relationships, and capacity fields.

Risk:

- Any intentional blocked/maintenance slot status is reset to `AVAILABLE`.
- If some Yard slots should stay blocked for validation, update them manually after cleanup.

## Review Notes

- The script uses physical table names from Prisma schema.
- Some operational Prisma models do not define `@@map`, so their physical PostgreSQL table names are PascalCase and quoted:
  - `"BOM"`
  - `"BOMItem"`
  - `"BOMRoutingStep"`
  - `"ComponentCosting"`
  - `"ProductionMaterialReservation"`
  - `"ProductionMaterialReservationLine"`
  - `"ProductionMaterialLedger"`
  - `"ProductionMaterialIssue"`
  - `"ProductionMaterialConsumption"`
- The script intentionally keeps `inventory_items`, so Scenario A should create a new validation material or reset only the selected validation material as part of test setup.

## Main Risks

- Operational history is removed from the validation database.
- Activity logs and outbox/job history are removed.
- Yard slot statuses are all reset to `AVAILABLE`.
- Existing inventory item snapshot quantities may remain non-zero while location stock is cleared.
- If attachments are linked only through QC operational rows, QC attachment link history is removed, but the generic attachment files/metadata are preserved because `attachments` is not truncated.
